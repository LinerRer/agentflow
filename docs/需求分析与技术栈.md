# AgentFlow 智能工作流平台 — 需求分析与技术栈

---

## 一、项目背景与痛点

大模型 Agent 工作流在实际运行中存在三大核心痛点：

1. **黑盒运行**：工作流跑起来后，无法直观看到内部执行到哪一步、每一步的输入输出是什么，出了问题只能靠猜。
2. **难以排错**：节点执行失败后，缺少完整的错误上下文和状态快照，无法快速定位是哪个节点、什么原因导致的失败。
3. **不可回溯**：任务执行完成后，无法回看历史执行过程，无法对比节点执行前后的状态变化，也无法复现问题。

AgentFlow 就是为了解决以上痛点而设计的**可观测、可回溯、可调试的智能工作流平台**。

## 二、核心需求

### 2.1 功能需求

| 模块 | 需求描述 | 优先级 |
|------|----------|--------|
| 工作流编排 | 基于 LangGraph 实现多节点工作流，支持节点注册、边连接、状态流转 | P0 |
| 任务管理 | 任务的创建、状态更新、列表查询、按状态筛选 | P0 |
| 全链路追踪 | 基于 trace_id 聚合任务、日志、快照、异常，形成完整执行时间线 | P0 |
| 状态快照 | 每个节点执行前后自动保存状态快照，支持版本管理和按版本恢复 | P0 |
| 执行回放 | 基于历史快照和日志，离线回放任务执行过程，支持单步和全量播放 | P0 |
| 单步调试 | 支持逐节点执行，执行完暂停，可查看和修改状态后继续 | P1 |
| 异常分级治理 | 按异常严重程度分三级（轻微/一般/严重），分别执行重试/跳过/终止策略 | P1 |
| 异常自动重试 | 轻微异常支持指数退避自动重试，重试耗尽后降级跳过 | P1 |
| 事件总线 | 发布-订阅模式，支持节点生命周期事件的监听和扩展 | P2 |
| 子任务管理 | 支持子任务的创建、串行执行、状态隔离与结果聚合 | P2 |
| 可视化前端 | Streamlit 搭建 Web 界面，支持任务提交、列表查看、追踪查询、回放操作 | P0 |

### 2.2 非功能需求

| 维度 | 要求 |
|------|------|
| 可扩展性 | 分层架构，新增业务节点无需修改核心代码 |
| 可维护性 | 业务逻辑与通用能力（日志、快照、重试）完全解耦 |
| 容错性 | 单个节点失败不影响整个任务，支持降级跳过 |
| 数据持久化 | 所有任务、日志、快照、异常自动落库 SQLite |
| 易用性 | 一键启动，Web 界面操作，无需命令行 |

## 三、系统架构

### 3.1 分层架构

```
┌─────────────────────────────────────────┐
│           表现层 (Presentation)          │
│         Streamlit Web 前端界面           │
├─────────────────────────────────────────┤
│           业务Agent层 (Agents)           │
│    数据分析Agent / 自定义业务节点         │
├─────────────────────────────────────────┤
│           核心能力层 (Core)              │
│  执行器 │ 快照 │ 追踪 │ 回放 │ 调试      │
│  异常处理 │ 事件总线 │ 子任务 │ 调度器    │
├─────────────────────────────────────────┤
│           数据持久层 (Storage)           │
│      DAO 模式封装 │ SQLite 数据库        │
├─────────────────────────────────────────┤
│           配置层 (Config)                │
│      全局参数 │ 常量配置 │ 路径管理       │
└─────────────────────────────────────────┘
```

### 3.2 各层职责

- **表现层**：只负责用户交互和数据展示，不包含业务逻辑
- **业务Agent层**：定义具体业务节点和工作流编排，只写业务代码
- **核心能力层**：提供通用基础能力，供所有业务复用，与具体业务无关
- **数据持久层**：封装所有数据库操作，上层不直接写 SQL
- **配置层**：所有可调参数集中管理，修改配置无需改代码

### 3.3 数据库设计

四张核心表，一对多关系：

| 表名 | 作用 | 关键字段 |
|------|------|----------|
| tasks | 任务元信息 | task_id, status, current_node, create_time |
| execution_logs | 执行日志 | log_id, task_id, trace_id, node_name, log_level, log_type, content |
| snapshots | 状态快照 | snapshot_id, task_id, node_name, snapshot_type, version, state_data, state_hash |
| exceptions | 异常记录 | exception_id, task_id, node_name, exception_type, error_type, error_message, error_stack |

## 四、技术栈

### 4.1 核心技术

| 分类 | 技术 | 版本/说明 | 用途 |
|------|------|-----------|------|
| 编程语言 | Python | 3.11 | 主开发语言 |
| 工作流引擎 | LangGraph | 最新版 | 基于状态机的多节点工作流编排 |
| 大模型框架 | LangChain | 最新版 | 大模型调用抽象层 |
| 大模型 | Ollama + Qwen2:7B | 本地部署 | 本地大模型推理，无需API Key |
| Web框架 | Streamlit | 最新版 | 快速搭建数据类Web界面 |
| 数据库 | SQLite | 内置 | 轻量级嵌入式数据库，无需额外安装 |

### 4.2 设计模式

| 模式 | 应用场景 |
|------|----------|
| 装饰器模式 | node_executor 节点执行器，统一封装日志、快照、重试、状态更新 |
| DAO模式 | 数据访问层，封装所有SQL操作，业务层不直接操作数据库 |
| 单例模式 | 快照管理器、回放器、追踪器、异常处理器、事件总线均为全局单例 |
| 策略模式 | 异常分级处理器，不同级别异常对应不同处理策略 |
| 发布-订阅模式 | 事件总线，事件发布与订阅完全解耦 |
| 工厂模式 | node_executor 装饰器工厂，接收节点名参数返回装饰器 |

### 4.3 核心设计思想

1. **关注点分离**：业务逻辑与通用能力（日志、快照、重试）彻底分开
2. **可观测性**：全链路留痕，每一步都有日志和状态快照
3. **容错降级**：异常分级处理，单个节点失败不挂整个任务
4. **状态驱动**：工作流基于统一状态字典流转，节点只负责读写状态
5. **配置驱动**：所有策略参数集中配置，调参不改代码

## 五、核心模块说明

### 5.1 节点执行器 (executor.py)

- 基于装饰器模式，给所有业务节点统一套上日志、快照、重试、状态更新能力
- 业务代码零侵入，只写业务逻辑
- 支持异常自动重试（可配置次数），重试耗尽后降级跳过
- 自动计算节点执行耗时

### 5.2 状态快照 (snapshot.py)

- 节点执行前后自动保存状态快照
- 版本号递增管理，支持按版本恢复
- MD5 哈希校验，确保快照完整性
- 可通过配置开关控制是否启用

### 5.3 全链路追踪 (trace.py)

- 基于 trace_id 聚合任务、日志、快照、异常
- 形成完整的执行时间线
- 支持按关键词搜索日志

### 5.4 执行回放 (replay.py)

- 纯读取历史数据，不重新执行任务，零消耗
- 将零散的日志和快照按节点、按顺序组装成回放步骤
- 支持单步前进、全量播放、重置

### 5.5 单步调试器 (debugger.py)

- 基于 LangGraph 的 stream 模式实现逐节点执行
- 每步执行完暂停，可查看当前状态
- 支持修改状态后继续执行
- 支持一次性执行完剩余步骤

### 5.6 异常分级处理器 (exception_handler.py)

- 三级异常分类：轻微（自动重试）、一般（降级跳过）、严重（终止任务）
- 轻微异常支持指数退避重试
- 统一返回处理结果，调用方按 action 执行

### 5.7 事件总线 (event_bus.py)

- 发布-订阅模式，支持事件注册、发布、订阅、取消订阅
- 订阅者异常隔离，单个订阅者崩溃不影响其他订阅者和总线
- 预定义节点和任务生命周期事件

### 5.8 子任务管理器 (subtask.py)

- 支持子任务创建，继承父任务 trace_id
- 串行执行多个子任务，状态隔离
- 子任务失败不中断父任务
- 支持结果聚合到父任务状态
